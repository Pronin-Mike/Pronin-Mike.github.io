# Серверный контракт ручного использования продукта

## Почему операция пока заблокирована

В текущей схеме есть атомарные серверные операции для покупки/ручной корректировки
(`mutate_fridge_item`), готовки (`cook_dish`) и выбрасывания (`waste_product`). Отдельной
операции обычного ручного использования нет.

Режим `adjust` нельзя безопасно выдавать за использование: это административная правка,
она записывает движение `adjustment`, не принимает нулевой итоговый остаток и поэтому не
может корректно удалить полностью использованный продукт. Локальное изменение React-state
тоже недопустимо: оно не атомарно и потеряется при следующем чтении Supabase.

## Минимальный контракт

Предлагаемая публичная функция:

```sql
public.consume_product(
  p_item_id uuid,
  p_amount numeric,
  p_operation_id uuid
) returns jsonb
```

RPC должна выполнять в одной транзакции:

1. Проверить `auth.uid()` и доступ пользователя в соответствии с действующей моделью RLS.
2. Заблокировать строку продукта через `select ... for update`.
3. Проверить, что количество — конечное число, больше нуля и не превышает остаток.
4. Рассчитать списываемые `total_cost` и `priced_amount` пропорционально текущему остатку,
   тем же способом округления, который уже используется в `cook_dish` и `waste_product`.
5. Записать движение с отдельной семантикой `movement_type = 'consume'` и
   `source = 'manual_use'`.
6. Обновить остаток и стоимость либо удалить `fridge_items`, если использован весь остаток.
7. Вернуть как минимум:

```json
{
  "consumed_amount": 300,
  "remaining_amount": 700,
  "cost": 60,
  "cost_complete": true
}
```

`p_operation_id` должен обеспечивать идемпотентность повтора запроса. Повтор той же операции
не должен списывать продукт второй раз и должен вернуть прежний результат.

## Необходимая согласованная миграция

Перед реализацией RPC потребуется расширить допустимые значения проверок
`product_movements.movement_type` и `product_movements.source` значениями `consume` и
`manual_use`. После этого функция должна получить те же ограничения доступа, что остальные
изменяющие RPC: `SECURITY DEFINER`, фиксированный `search_path`, отозванный доступ у
`PUBLIC`/`anon` и `grant execute` только роли `authenticated`.

Эта миграция в этапе 2 **не выполнялась**: изменение схемы требует отдельного согласования.
После её применения фронтенду достаточно добавить типизированный метод в `src/lib/api.ts`
и включить уже подготовленную кнопку подтверждения в сценарии «Использовать».
