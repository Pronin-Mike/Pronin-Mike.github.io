# 🍳 Домашняя кулинарная книга

Персональная кулинарная книга: рецепты по разделам, холодильник с продуктами, сроки годности и
честный ответ на вопрос «что можно приготовить прямо сейчас». Хостинг — статика на
**GitHub Pages**, данные — в **Supabase** (PostgreSQL + Auth + RLS), своего бэкенда нет.

**Стек:** React 18 · Vite 5 · TypeScript (strict) · TailwindCSS 3 · @supabase/supabase-js ·
react-router-dom (HashRouter) · lucide-react · vitest (тесты).

## 1. Быстрый старт

```bash
npm install

# ключи Supabase (Project Settings → API)
cp .env.example .env.local       # Windows: copy .env.example .env.local

npm run dev                      # http://localhost:5173
```

Пользователей регистрация не создаёт: аккаунт заводится вручную в
**Supabase → Authentication → Users → Add user**, затем вход на `/login`.

| Команда | Что делает |
|---|---|
| `npm run dev` | dev-сервер Vite |
| `npm run build` | `tsc --noEmit` (строгая проверка типов) + сборка в `dist/` |
| `npm run preview` | локальный просмотр собранного `dist/` |
| `npm run typecheck` | только проверка типов |
| `npm test` | 110 тестов (vitest): логика + интерфейс в jsdom |

Если переменные окружения не заданы, приложение не падает, а показывает экран с инструкцией
(`ConfigNotice` в [src/App.tsx](src/App.tsx)).

## 2. Архитектура

### 2.1 Слои и направление зависимостей

Проект разделён на слои, и зависимости идут строго в одну сторону — сверху вниз.
Это позволяет тестировать логику без сети и DOM, а компоненты держать «глупыми».

```
                    ┌──────────────────────────────────────────────┐
   UI-слой          │  pages/*  (маршруты, формы, фильтры, busy)    │
                    │  components/*  (карточки, модалки, поля)      │
                    └───────────────┬──────────────────────────────┘
                                    │ useCookbook()  +  прямые вызовы api
                    ┌───────────────▼──────────────────────────────┐
   Слой состояния   │  hooks/useCookbook.ts                        │
                    │  загрузка, reload, reloadFridge, cook()       │
                    └───────────────┬──────────────────────────────┘
                                    │
                    ┌───────────────▼──────────────────────────────┐
   Слой данных      │  lib/api.ts   ← ЕДИНСТВЕННОЕ место с         │
                    │  запросами к Supabase + нормализация строк    │
                    └───────────────┬──────────────────────────────┘
                                    │
                    ┌───────────────▼──────────────────────────────┐
   Клиент           │  lib/supabase.ts  createClient<Database>      │
                    └───────────────┬──────────────────────────────┘
                                    ▼
                       Supabase: PostgREST + Auth + RLS → PostgreSQL

   ─────────────────────────────────────────────────────────────────
   Чистые модули (никакой сети и DOM, только вход → выход):
   lib/availability.ts · lib/suggestions.ts · lib/fridgeImport.ts
   lib/csv.ts · lib/shelfLife.ts · lib/validation.ts · lib/format.ts
   Их вызывают и страницы, и тесты. Это самая покрытая тестами часть.
```

Правила, которые соблюдаются в коде:

* **компоненты не знают про Supabase** — только `hooks/useCookbook` и функции `lib/api.ts`;
* **логика не знает про React** — расчёты живут в чистых функциях `lib/*`;
* **данные из БД не «протекают» в UI** — `api.ts` превращает строки (`snake_case`, `string`
  в `unit`) в доменные объекты (`Dish`, `FridgeItem`, `Section`) с проверенными типами;
* **ошибки не глотаются** — `api.ts` превращает ошибку PostgREST в `Error` с понятным
  русским контекстом, страница показывает её тостом.

Единственное осознанное исключение: `components/FridgeCsvImport.tsx` — это самодостаточный
блок фичи «импорт холодильника», он сам вызывает `api.applyFridgeImport`. Такой «умный
компонент» вынесен отдельно, чтобы страница `Import.tsx` оставалась читаемой.

### 2.4 Состояние данных: `useCookbook`

[hooks/useCookbook.ts](src/hooks/useCookbook.ts) — единственный «контейнер данных».
Он загружает разделы, блюда и холодильник и отдаёт страницам:

```ts
interface CookbookData {
  sections: Section[];
  dishes: Dish[];
  fridge: FridgeItem[];
  fridgeIndex: Map<string, FridgeItem>;   // индекс «название|единица» → продукт
  expiring: FridgeItem[];                 // soon + today, по возрастанию даты
  expired: FridgeItem[];                  // просроченные
  loading: boolean;
  error: string | null;
  reload: () => Promise<void>;            // перечитать всё
  reloadFridge: () => Promise<void>;      // перечитать только холодильник
  cook: (dishId: string) => Promise<CookResult>;  // RPC cook_dish + обновление холодильника
}
```

* `fridgeIndex` строится через `useMemo` из `indexFridge()` — доступность каждого блюда
  считается `checkDish(dish, fridgeIndex)` без повторных проходов по массиву;
* `cook()` вызывает серверную функцию и, если она вернула `success: true`, перечитывает
  холодильник — карточки сразу становятся серыми, ничего не нужно перезагружать вручную;
* перед списанием `cook()` сверяет ингредиенты блюда с холодильником и добавляет в результат
  `expiredWarning` — список просроченных продуктов, которые всё равно были списаны (для тоста);
* `expiring` / `expired` считаются из холодильника тем же `getExpiryStatus`, что и бейджи, —
  отдельного состояния для сроков нет;
* каждая страница держит свой экземпляр хука и перечитывает данные при монтировании,
  поэтому после импорта или правки переход на «Рецепты» показывает свежее состояние.

**Никакого redux / react-query / zustand.** Данных мало (личная книга), а сервер — источник
правды. Локальные состояния страниц (`useState`) отвечают за формы, поиск, фильтры и
признак «идёт операция».

### 2.5 Работа с Supabase

**[lib/supabase.ts](src/lib/supabase.ts)** — единственное место создания клиента:

```ts
export const isSupabaseConfigured = /^https?:\/\/.+/.test(url) && anonKey.length > 20;
export const supabase = createClient<Database>(url, anonKey, {
  auth: { persistSession: true, autoRefreshToken: true, detectSessionInUrl: false }
});
```

`detectSessionInUrl: false` — потому что приложение на HashRouter и magic-link/OAuth-редиректы
не используются.

**Типизация схемы.** В [types.ts](src/lib/types.ts) описаны и строки таблиц, и объект
`Database` — так `supabase.from('dishes').select('*')` возвращает типизированные строки, а не
`any`. Важная деталь: строки БД объявлены через `type`, а **не** `interface`. Только
объектные типы-алиасы получают неявную индексную сигнатуру; с `interface` схема не проходит
проверку `GenericSchema` в `@supabase/postgrest-js`, и все запросы становятся `never`. В коде
это отмечено комментарием.

**Нормализация.** Всё, что приходит из БД, проходит через `toDish`, `toFridgeItem`, `toSection`,
`normalizeIngredients`:

* `unit: string` → `Unit` (`'г' | 'мл' | 'шт'`) с запасным значением;
* `dishes_full.ingredients` приходит jsonb-агрегатом: принимается и массив, и строка JSON,
  сортируется по `sort_order`;
* `steps` может быть `null` — приводится к пустому массиву.

**Резервный путь чтения.** `fetchDishes()` сначала спрашивает view `dishes_full`; если она
недоступна (нет прав или не создана), тихо переходит на выборку из `dishes` +
`dish_ingredients` и группировку на клиенте. Поэтому книга работает даже при неполной схеме.

**Запись.** `createDish` вставляет блюдо и ингредиенты; `updateDish` обновляет запись блюда и
перезаписывает ингредиенты (delete + insert — проще и надёжнее, чем diff);
`importBackup` сначала удаляет блюда (каскадом уходят ингредиенты) и холодильник, затем
вставляет данные заново.

### 2.6 Аутентификация и маршруты

Поток авторизации:

```
AuthProvider (context/AuthContext.tsx)
  ├─ getSession() при монтировании  → loading=false, session|null
  ├─ onAuthStateChange(...)         → сессия всегда актуальна (refresh, выход в другой вкладке)
  ├─ signIn(email, password)        → signInWithPassword + перевод ошибок на русский
  └─ signOut()
        │
ProtectedRoute  ── loading → спиннер
                ── нет сессии → <Navigate to="/login" state={{ from }} />
                ── есть сессия → <Outlet/> (Layout → страница)
```

Регистрации нет (`signUp` не вызывается) — пользователей создаёт владелец в панели Supabase.
Частые ошибки входа переводятся в человеческий текст («Invalid login credentials» →
«Неверный email или пароль.», «Email not confirmed» → «Email не подтверждён…»).

Маршруты (`src/App.tsx`, HashRouter):

| Маршрут | Страница | Доступ |
|---|---|---|
| `/login` | `Login` | публичный |
| `/` | `Recipes` | только с сессией |
| `/fridge` | `Fridge` | только с сессией |
| `/dish/new` | `DishEdit` | только с сессией |
| `/dish/:dishId/edit` | `DishEdit` | только с сессией |
| `/import` | `Import` | только с сессией |
| `/settings` | `Settings` | только с сессией |
| `/:sectionId/:dishId` | `DishDetail` | только с сессией |
| `*` | редирект на `/` | — |

Выбранный раздел хранится в адресе (`/?section=lunch`) — на него можно дать ссылку, и
кнопка «К рецептам» из блюда возвращает в нужный раздел.

### 2.7 Ошибки, загрузка, уведомления

| Ситуация | Как обрабатывается |
|---|---|
| Ошибка чтения (списки) | `useCookbook.error` → карточка «Не удалось загрузить…» с кнопкой «Повторить» |
| Ошибка записи (insert/update/delete/RPC) | `raise('Не удалось сохранить блюдо', error)` → `catch` на странице → `toast.show(message, 'error')` |
| Операция выполняется | локальный `busy` → кнопки `disabled`, текст «Сохраняем…»/«Импортируем…» |
| Первичная загрузка | `loading` → `SkeletonCards` / `SkeletonRows` / `FullScreenSpinner` |
| Успех | тост «Блюдо сохранено», «Холодильник обновлён — добавлено: 3…» (3 с, ошибки 5 с) |
| Нехватка продуктов при готовке | `cook_dish` вернул `success:false` → тост со списком `missing` |

Шаблон «мутация + интерфейс» на страницах:

```ts
const run = async (task: () => Promise<unknown>, successMessage: string) => {
  setBusy(true);
  try {
    await task();
    toast.show(successMessage, 'success');
    await reloadFridge();
  } catch (caught) {
    toast.show(caught instanceof Error ? caught.message : 'Не удалось выполнить операцию', 'error');
  } finally {
    setBusy(false);
  }
};
```

### 2.8 Стили и дизайн-система

Tailwind, конфигурация в [tailwind.config.js](tailwind.config.js). Палитра вынесена в токены:

| Токен | Назначение |
|---|---|
| `cream-50…400` | тёплый бежевый фон и границы |
| `terra-50…700` | основной акцент: кнопки, активные чипы, ссылки |
| `olive-*` | «можно готовить», успешные операции |
| `honey-*` | предупреждения (не хватает продуктов, режим «заменить») |
| `berry-*` | ошибки и удаление |
| `ink`, `ink-soft`, `ink-muted` | текст трёх уровней |

Плюс `shadow-soft / lift / sheet`, анимации `fade-in`, `rise-in`, `sheet-in`, `toast-in`,
шрифты: системный стек + `Georgia` для заголовков (никаких внешних шрифтов — сайт работает
офлайн и не тянет запросы на сторонние CDN).

Ключевые решения по интерфейсу:

* **mobile-first**: базовая вёрстка — телефонная, `md:` расширяет сетку до 2–3 колонок,
  навигация снизу (`fixed`) переезжает в шапку (`Layout.tsx`, брейкпоинт `md`);
* **тач-таргеты** не меньше 44 px (`min-h-11` у кнопок и ссылок навигации);
* **без фотографий**: визуальное разнообразие — эмодзи разделов (🍳 🍲 🍽) и цветовые акценты;
* **доступность**: `aria-label` у иконочных кнопок, `role="dialog" aria-modal` и возврат
  фокуса в `Modal`, `role="combobox"/"listbox"` в подсказках ингредиентов, `aria-live` у тостов,
  `:focus-visible` обводка, учёт `prefers-reduced-motion` в [index.css](src/index.css).

### 2.9 Чистая логика и тесты

Вся предметная логика живёт в `lib/*` и покрыта unit-тестами. Это дало конкретный выигрыш:
во время разработки тесты поймали реальные баги (например, молчаливую подмену невалидной
единицы `кг` на `г` при импорте CSV холодильника и потерю продуктов при нормализации списка).

Пирамида:

* **unit** — `availability`, `suggestions`, `fridgeImport`, `csv`, `shelfLife` (90 тестов, без DOM и сети);
* **integration (jsdom)** — `App.test.tsx`: реальные клики по карточкам, формы, модалки,
  импорт, подсказки, сроки годности; Supabase и `api.ts` заменены моками (20 тестов);
* **статических проверок сборки** нет отдельно — их роль выполняет `tsc --noEmit` в `npm run build`.

## 3. Функциональность и правила

### 3.1 Доступность блюда

1. Название сравнивается без учёта регистра и лишних пробелов: `normalizeName` → `lower` + сжатие пробелов.
2. Единица измерения должна совпадать **точно**: `г`, `мл`, `шт` между собой не пересчитываются.
3. Количества в холодильнике должно быть не меньше требуемого (сравнение с `EPS = 1e-9`).
4. Никаких синонимов: «масло 30 г» не найдётся при «масло 200 мл» — блюдо станет серым
   с пометкой «Не хватает: масло 30 г».

`checkDish()` возвращает `{ available, missing: [{name, need, have, unit, reason}], missingText, ready, total }`,
где `reason` — `absent` (нет продукта), `unit` (есть, но в другой единице), `short` (мало).

### 3.2 Приготовление

Кнопка «Приготовить» (в карточке и в просмотре блюда) вызывает RPC `cook_dish(p_dish_id uuid)`:

* функция проверяет наличие всех ингредиентов на стороне БД (атомарно);
* при нехватке возвращает `{success:false, missing:[…]}` → тост со списком;
* при успехе списывает продукты, удаляет обнулившиеся позиции, пишет строку в `cook_log`
  и возвращает `{success:true}` → фронтенд перечитывает холодильник и показывает тост
  «…приготовлено — продукты списаны».

Важно: проверка и списание происходят **в базе**, поэтому две вкладки не могут списать
продукты дважды «одновременно по своим расчётам».

### 3.3 Холодильник

* Быстрое добавление сверху, правка в той же форме, удаление с подтверждением, поиск,
  сортировка по названию (`localeCompare('ru')`), «Очистить холодильник».
* Дубликат определяется по `normalizeName(name) + unit`. Если продукт уже есть — диалог
  **Заменить / Сложить / Отмена** (замена или суммирование количества в существующей строке).
* Ограничение `unique (name, unit)` в БД: обновление единицы может конфликтовать —
  тогда ошибка Postgres показывается тостом как есть.

### 3.4 Сроки годности

Срок годности — необязательная дата `expires_at` (`date`, `YYYY-MM-DD`) у продукта в
холодильнике. Логика целиком в [lib/shelfLife.ts](src/lib/shelfLife.ts), запись — в `api.ts`.

* **Автоподстановка.** Как только в форме продукта введено название (и дату ещё не правили
  руками), подставляется типовой срок: молоко — 7 дней, сыр — 14, рыба — 2, хлеб — 3, яйца — 30.
  Таблица `SHELF_LIFE_DAYS` ищет **самое длинное совпадение-подстроку**, поэтому «Молоко 3,2%»
  тоже даёт 7 дней.
* **«Вечные» продукты** (`ETERNAL_PRODUCTS`: соль, сахар, мука, крупы, консервы, мёд, специи,
  масло растительное, …) автодаты не получают — срок ставится только вручную.
* **Быстрые чипы** `+1д +3д +7д +14д +30д` рядом с полем даты; дата в прошлом подтверждается
  диалогом «Это просроченный продукт?».
* **Статусы** (`getExpiryStatus`): `expired` (дата прошла), `today`, `soon` (≤ 3 дней),
  `ok`, `none` (даты нет). Бейдж `ShelfLifeBadge` показывает «17 окт · через 3 дня», у
  просроченного — с префиксом «⚠».
* **Сортировка и фильтр** в холодильнике: «По названию / По сроку» (просроченное, скоро,
  сегодня, дальше, без срока) и чекбокс «Только истекающие». Переход
  `/fridge?sort=expiry` из блока «Скоро истекает» включает сортировку по сроку.
* **Складывание продуктов** (диалог «Заменить / Сложить»): при сложении остаётся более ранняя
  дата, `null` не перекрывает дату.
* **Влияние на готовку.** Просроченное **не считается отсутствующим**: `checkDish` не меняется,
  блюдо остаётся доступным, но карточка получает красный бейдж «Просрочено: …», а после
  `cook()` показывается предупреждающий тост «Приготовлено. Использованы просроченные
  продукты: …» (5 секунд). Списание при этом выполняется.
* **Рецепты.** Над фильтрами — блоки «Просрочено» (с кнопками «Выбросить» / «Выбросить всё»)
  и «Скоро истекает» (до 5 позиций, «Показать все»). В режиме «Что приготовить» выше стоят
  блюда, которые «спасают» больше продуктов со статусом `soon`/`today`.

### 3.5 Подсказки ингредиентов в форме блюда

* поиск **по началу названия**: «о» → `огурцы`, `орехи`; «ог» → только `огурцы`;
  регистр и лишние пробелы не важны;
* в подсказке видна единица измерения, при выборе подставляются **название и единица** —
  ингредиент сразу совпадёт с холодильником;
* **если продукта нет — список закрывается**, поле работает как обычный ввод;
* пустое поле подсказок не показывает; выбор мышью, `↑`/`↓` + `Enter`, `Esc` закрывает.

### 3.6 Импорт

**Холодильник из CSV** (`name,amount,unit,expires_at`) — предпросмотр считает `planFridgeImport`:

| Режим | Поведение |
|---|---|
| `merge` (по умолчанию) | совпадающие названия обновляются, новые добавляются; дата из файла перекрывает текущую, пустая — оставляет прежнюю (а если её не было, ставится типовой срок) |
| `sum` | количества складываются; при несовпадении единицы строка пропускается с предупреждением; срок годности — минимальный из двух (`null` не перекрывает дату) |
| `replace` | холодильник заменяется содержимым файла; сроки берутся только из файла, пустые — по таблице типовых сроков |

План отдаёт `inserts` / `updates` / `deletes`, а `api.applyFridgeImport(plan)` их применяет —
предпросмотр и запись используют один и тот же объект, разойтись не могут.

**Блюда из CSV** (`title,section,ingredients,time,steps,notes`) — таблица «что будет добавлено»
и ошибки с номерами строк; строки с ошибками пропускаются, корректные вставляются
по одной через `api.importDishes` (отчёт «Добавлено X блюд, ошибок Y»).

**JSON-бэкап** — экспорт `{fridge_items, dishes, dish_ingredients}` в файл; импорт полностью
заменяет содержимое базы, предварительно спросив подтверждение и показав, сколько чего в файле.

## 4. Схема БД, которую ожидает фронтенд

Схема создаётся в Supabase заранее; фронтенд только читает и пишет.

| Объект | Что используется |
|---|---|
| `sections` | `id text`, `title_ru text`, `sort_order int`; строки `breakfast/Завтрак`, `lunch/Обед`, `dinner/Ужин` |
| `fridge_items` | `id uuid`, `name text`, `amount numeric`, `unit text`, `expires_at date null`, `updated_at`; ограничения `unique (name, unit)`, `unit in ('г','мл','шт')`, `amount >= 0`, `fridge_expires_at_sane` (в пределах ±365 дней от `current_date`), индекс `idx_fridge_items_expires_at` |
| `dishes` | `id uuid`, `title`, `section_id → sections.id`, `time_min int null`, `steps text[]`, `notes text`, `created_at`, `updated_at` |
| `dish_ingredients` | `id uuid`, `dish_id → dishes.id on delete cascade`, `name`, `amount numeric`, `unit`, `sort_order int` |
| `cook_log` | `id uuid`, `dish_id → dishes.id on delete set null`, `cooked_at` |
| view `dishes_full` | `id, title, section_id, time_min, steps, notes, ingredients` — jsonb-массив `{name, amount, unit, sort_order}` |
| функция `cook_dish(p_dish_id uuid)` | `returns jsonb`: `{"success": true}` либо `{"success": false, "missing": [{name, need, have, unit}]}` (ключ `amount` вместо `need` тоже принимается) |

RLS включён на всех таблицах, политики разрешают работу только роли `authenticated`.
Разделов ровно три: `breakfast`, `lunch`, `dinner` (блюдо с разделом `snack` при импорте
отклоняется с понятной ошибкой).

## 5. Форматы CSV и JSON

### 5.1 Холодильник: `name,amount,unit,expires_at`

```csv
name,amount,unit,expires_at
творог,500,г,2026-10-15
молоко,1000,мл,2026-10-14
соль,300,г,
яйца,10,шт,2026-11-07
```

Строка заголовков необязательна; разделитель — `,`, `;` или табуляция; понимаются русские
заголовки (`название`, `количество`, `единица`, `срок годности`) и латиница в единицах
(`g`, `ml`, `pcs`); дробное количество с запятой проходит, при разделителе `,` поле берётся
в кавычки. Колонка `expires_at` **необязательна** — без неё все даты считаются пустыми;
формат `ГГГГ-ММ-ДД`, пустое значение — «срока нет» (тогда при импорте подставится типовой
срок хранения). Неверный формат даёт ошибку с номером строки. Пример:
`public/examples/sample-fridge.csv`. Обратная операция — «Экспорт холодильника».

### 5.2 Блюда: `title,section,ingredients,time,steps,notes`

```csv
title,section,ingredients,time,steps,notes
Омлет с сыром,breakfast,яйца|3|шт;сыр|50|г;молоко|50|мл,15,"Взбить яйца;Добавить сыр;Обжарить",Солить в конце
```

* `section` — `breakfast` | `lunch` | `dinner` (можно по-русски);
* `ingredients` — элементы через `;`, каждый `название|количество|единица`;
* `steps` — шаги через `;`; `time` — минуты, можно пусто.

Пример: `public/examples/sample-recipes.csv`, шаблон — кнопкой «Скачать шаблон».

### 5.3 JSON-бэкап

```json
{
  "app": "home-cookbook",
  "version": 1,
  "exportedAt": "2025-01-01T09:00:00.000Z",
  "fridge_items": [ … ],
  "dishes": [ … ],
  "dish_ingredients": [ … ]
}
```

Пример: `public/examples/sample-backup.json`. Импорт генерирует новые `id`, сохраняя связи
«блюдо → ингредиенты».

## 7. Деплой на GitHub Pages

### Вариант 1 (рекомендуется): GitHub Actions

1. Пуш в ветку `main`.
2. **Settings → Secrets and variables → Actions**: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`.
3. **Settings → Pages → Source: GitHub Actions.**
4. Workflow прогонит `typecheck`, тесты, соберёт `dist/` с `VITE_BASE_PATH=/<имя-репозитория>/`
   и опубликует артефакт.

### Вариант 2: вручную

```bash
VITE_BASE_PATH=/<репозиторий>/ npm run build
npx gh-pages -d dist          # или залейте содержимое dist/ в ветку gh-pages
```

**Про `base`.** Vite кладёт статику в `/assets/…`, поэтому для project site нужен префикс с
именем репозитория, иначе браузер запросит файлы из корня домена и получит 404. Значение
читается из `VITE_BASE_PATH` (по умолчанию `/` — случай user site).

**Про прямые ссылки.** Используется `HashRouter`, адреса выглядят как `…/#/fridge`, поэтому
обновление страницы и переход по прямой ссылке не дают 404 (статика на Pages не умеет
отдавать `index.html` для произвольных путей).

`anon key` вшивается в бандл при сборке — так и задумано: доступ к данным закрывают
RLS-политики. В репозиторий попадает только `.env.example`.

## 10. Осознанные решения и ограничения

**Почему так:**

* **HashRouter вместо BrowserRouter** — GitHub Pages не умеет отдавать `index.html` на
  произвольный путь, иначе прямые ссылки давали бы 404.
* **Без redux / react-query** — один хук на страницу проще читать и отлаживать при личном
  объёме данных; сервер остаётся источником правды.
* **Свой CSV-парсер** вместо `papaparse` — ноль зависимостей и полный контроль над
  сообщениями об ошибках с номерами строк.
* **Логика доступности на клиенте, списание — в БД.** Клиент рисует серые карточки, а
  проверка и списание продуктов выполняются атомарно функцией `cook_dish`.
* **Tailwind + 13 своих компонентов** вместо UI-кита — меньше веса и полный контроль вида.
* **Никаких внешних шрифтов и картинок** — сайт не делает запросов на сторонние домены.
* **`localStorage` не используется для данных** (только сессия Supabase Auth, как это
  устроено в самой библиотеке).

**Чего нет (и почему):**

* регистрации, восстановления пароля, профилей — пользователь один, аккаунт заводится в панели;
* загрузки фотографий блюд — по исходной задумке вместо них эмодзи;
* полдника — в схеме БД ровно три раздела;
* офлайн-режима и кэша данных — книга живёт на сервере;
* пагинации и виртуализации списков — данных личного масштаба.

**Известные компромиссы:**

* `opacity-50` у недоступной карточки снижает читаемость — поэтому бейдж «Не хватает: …»
  вынесен за пределы полупрозрачной области;
* обновление единицы измерения продукта может нарушить `unique (name, unit)` — в этом случае
  пользователь видит исходный текст ошибки Postgres;
* типовые сроки хранения — усреднённые (молоко 7 дней, рыба 2 дня): они подставляются как
  подсказка, но реальный срок зависит от упаковки и холодильника, поэтому дату можно поправить;
* просроченный продукт не блокирует готовку — приложение предупреждает (бейдж и тост), но
  решение остаётся за пользователем;
* страницы читают все блюда целиком (без пагинации) — при личной книге это быстрее и проще.

## 11. FAQ

**Экран «Нужны ключи Supabase».** Не заданы `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`
(локально — `.env.local`, на Pages — секреты Actions). Переменные вшиваются при сборке,
поэтому после правки нужен перезапуск `npm run dev` или пересборка.

**Вход не проходит.** Пользователь должен существовать в Supabase Authentication → Users.
«Invalid login credentials» — неверная пара email/пароль; «Email not confirmed» — подтвердите
пользователя в панели.

**Пустой список рецептов после входа.** Проверьте RLS: политики должны разрешать
`authenticated` доступ к таблицам и view. И что в `sections` есть три строки — разделы
берутся из базы.

**Файл с продуктами не импортируется.** Для холодильника есть отдельный блок «Холодильник
из CSV» (формат `name,amount,unit,expires_at`). Если вставить такой файл в блок блюд, парсер
подскажет: «Похоже, это CSV холодильника…». Единицы — `г`, `мл`, `шт` (`g`, `ml`, `pcs` тоже
принимаются; `кг`, `л`, `ст.л.` — нет).

**Срок годности не подставился.** Автодата появляется, когда продукт есть в таблице типовых
сроков (`shelfLife.ts`) и не относится к «вечным» (соль, мука, крупы, консервы…). Дату можно
задать вручную или чипами «+1д … +30д». БД принимает дату только в пределах ±365 дней от
сегодня (`fridge_expires_at_sane`) — при дате в прошлом сначала спрашиваем подтверждение.

**Сборка падает на `base`.** Для project site нужен `VITE_BASE_PATH=/<репозиторий>/`
(в workflow подставляется автоматически).

## 12. Прежняя версия (`legacy-static`)

В папке [legacy-static/](legacy-static/README.md) лежит первая реализация: чистые HTML + CSS +
JavaScript, данные в `localStorage`, четыре раздела, свой импорт CSV холодильника. Vite её не
собирает (`index.html`, `src/` и `public/` — единственные источники сборки), в `dist/` она не
попадает. Оставлена как рабочий офлайн-вариант и как история решений.
